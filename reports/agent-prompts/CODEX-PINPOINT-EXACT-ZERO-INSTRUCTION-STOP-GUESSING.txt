НОВЫЙ МЕТОД — ПИНПОЙНТ точной инструкции обнуления (не кандидаты):
Ты уже доказал: source иконки ЦВЕТНОЙ → DIB-fill сохраняет → vector-memory (MOVDQU/
MOVDQA) ТОЧНЫ → ноль появляется на границе ImageList copy. Теперь НАЗОВИ ТОЧНУЮ
операцию, которая делает ноль. Не «может rep movs, может pack» — а конкретный PC+байты.

ШАГ 1 — найди МОМЕНТ перехода non-zero→zero:
- В ImageList ingest/draw найди буфер, который ДО операции содержит цветные пиксели
  (source), а ПОСЛЕ — нули (dest). Это ты уже локализовал.
- Инструментируй ИМЕННО эту операцию: дампни PC, опкод-байты, disasm инструкции(й),
  которые читают source и пишут dest на этом шаге.

ШАГ 2 — развилка (дамп решает за раз):
A. Инструкция читает ПРАВИЛЬНЫЙ source-адрес, но что гость ЧИТАЕТ по нему = нули,
   хотя в HOST-памяти по тому же адресу данные есть → баг **memory mapping**
   (virtual.c guest-read, см. reports/engine-audit/ICON-LOWER-LAYER-AUDIT.md). Тогда
   инструкция ни при чём — копай virtual.c guest memory read.
B. Гость читает source правильно (данные есть), но инструкция-копир пишет ноль/не
   пишет → ВОТ ОНА. Назови опкод (PC+байты), проверь декодируется ли / правильно ли
   транслируется. Это и есть кандидат на фикс (не гадательный).
C. Инструкция читает НЕ ТОТ адрес (source указывает на нулевой/неинициализированный
   буфер) → проблема выше: где ImageList выбирает source.

ШАГ 3 — только ПОСЛЕ пинпойнта:
- Если это инструкция (B) — добавь её family (decode/IR/lift/interp/JIT/tests).
- Если memory (A) — чини virtual.c guest-read.
- Если source-выбор (C) — чини где ImageList берёт буфер.
НЕ добавляй больше инструкций «на всякий случай» — только подтверждённую.
