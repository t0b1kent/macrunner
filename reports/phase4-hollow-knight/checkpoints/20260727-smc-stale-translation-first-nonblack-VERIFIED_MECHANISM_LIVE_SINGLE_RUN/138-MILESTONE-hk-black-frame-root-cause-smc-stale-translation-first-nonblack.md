# 138 — MILESTONE: чёрный кадр оказался не графикой; найдена дыра в инвалидации трансляций — и впервые появились пиксели

Продолжает [[137-MILESTONE-hk-worker-thread-death-cured-TLS-shadow-frame-overturned]].

> [!important] Главное
> Сутки автономных лайнов сняли графику с подозрения **послойно**, доказали, что чернота — это **остановка managed-бутстрапа Mono**, а затем разбор чужой спецификации (Мигоцка, автор xtajit/xtajit64) вскрыл конкретный баг у нас: **гостевой сброс кэша инструкций не инвалидировал ни одной трансляции**. Лайн доказал механизм живьём — и **детектор регрессии впервые перевернулся: презентуемая поверхность не чёрная**.

## Часть 1. Чернота — не графика (вердикт)

Доказательство **дифференциальное**, а не «мы этого не увидели в логе». Наш `Player.log` против лога Windows-Prism-оракула после одной и той же строки: общий маркер `Game controller set to None.` есть у обоих (значит трейс живой), а дальше **каждый** маркер оракула у нас = 0, в обоих прогонах:

| Маркер | оракул | run-1 | run-2 |
|---|---|---|---|
| `Loaded saved language code 'EN'` | 1 | **0** | **0** |
| `Making UI menu lean.` | 1 | **0** | **0** |
| `Opening_Sequence` fallbacks | 3 | **0** | **0** |
| имена сцен | есть | **0** | **0** |
| `Screen position out of view frustum` | **0** | 19817 | 17927 |

Воспроизведено A/A: readback presented-surface на `Present ordinal 200`, **побитово одинаковый хеш** `0xc770038f717d0383`, `black=786432 nonblack=0`.

**Графика оправдана послойно** — не переоткрывать без новых улик:
- причинная лестница C2 (вход фрагмента) и C3 (выход вершинного регистра) дают **полноэкранную магенту** 655360/655360;
- 152/152 реальных DXBC-блоба HK транслируются чисто, 82/82 PS пишут в rt0, паритет `discard` 28/28, шейдеров с `o0_writes==0` — ноль;
- композиция биндит backbuffer RTV в 210/210 последних привязок перед `Present1`;
- чёрные вершинные цвета `(0,0,0,5/255)` пишет **сама Unity**;
- матричная арифметика SSE совпадает с x86, MXCSR `0x1f80`, host `FPCR=0x0`.

## Часть 2. Как чужая спека дала наш баг за полчаса

Разбор [ARM64 Boot Camp](http://www.emulators.com/docs/abc_exit_xta.htm) Дарека Мигоцки — **одного из инженеров Microsoft, сделавших TTD, xtajit, xtajit64 и xtabase**. Это не обзор со стороны, а описание конструкции, которую мы воспроизводим, автором этой конструкции.

Ключевая фраза: *сброс кэша инструкций посылает колбэк в x64-транслятор, чтобы тот сбросил закэшированные трансляции*. И он это **измеряет**: один `FlushInstructionCache()` на итерацию горячего цикла — **×50 замедления для эмулируемого x64 и ×300 для нативного ARM64**. Значит правильный транслятор делает там серьёзную работу.

Проверка нашей цепочки — и она рвётся на последнем шаге:

1. `signal_arm64ec.c:771` — Wine честно зовёт `pBTCpu64FlushInstructionCache( addr, size )` ✅
2. `xtajit64/cpu.c:198` — **диапазон выбрасывается**, в unix уходит `NULL` ❌
3. `xtajit64/unixlib.c:710` — `return STATUS_SUCCESS;`, **заглушка** ❌
4. `hb_cache_invalidate*` (`hb_aot_cache.c:452,473`) — **ни одного боевого вызова**, только тесты, и гранулярность не та (модуль/версия, а не диапазон адресов)

Заодно проверено и оказалось **не** дырой: `VirtualAlloc2` с `MEM_EXTENDED_PARAMETER_EC_CODE` у нас обрабатывается в боевом коде (`ntdll/unix/virtual.c:6481,6544`), EC bitmap на месте.

## Часть 3. Механизм доказан живьём — и первые пиксели

Лайн `hk-mono` построил байтовый ре-хеш трансляций. Сначала **поймал сам себя** на той ошибке, которая обнулила две прошлые попытки: хук стоял в `hb_jit_runtime_run_legacy`, а живая игра идёт через `SINGLE_LOOKUP hb_jit_runtime_run` — прибор молча мерил пустоту (класс `WRONG_HELPER_STATE`). Починил, вытащил заодно настоящий use-after-free (вытеснение уничтожало блок, уже одолженный быстрым путём), и доказал контроль на **обоих** путях плюс в выключенном режиме.

Живой прогон (run5):
- **гостевой код действительно переписывается за спиной закэшированных трансляций**: 3295 вытеснений при 60681 отслеженном блоке и 83.9 млн проверок, `unreadable=0`;
- подпись физически осмысленная — спаны **32–35 байт на соседних адресах**, размер и кучность **трамплинов Mono**, перенацеливаемых по мере компиляции методов;
- **детектор перевернулся**: ordinal-200 `hash=0xf7ea9ca044b2fdb5`, `nonblack=11968`, серое R=G=B до белого, ~1.5% кадра. В обоих прошлых прогонах было `nonblack=0` побитово.

> [!warning] Чего этот майлстоун НЕ утверждает
> Нецветной кадр — **один прогон**, A/A подтверждения пока нет. Run5 **не дошёл** до `Performing automatic level start.` за 3000с, хотя прошлые доходили: ре-хеш стоит ~2× на диспетчеризации, а разрыв с оракулом (33.9с на весь путь) сейчас больше 88×. И главное — **оставшийся стопор это НЕ устаревшая трансляция**: вытеснения прекратились на +1017с, прибор остался живым (+16.8 млн проверок), а игра жгла 120–140% CPU. Лайн опроверг собственную гипотезу своим же прибором.

## Часть 4. Метод, который это дал

Три автономных лайна в лупе с цепочкой отказа `codex → kimi → claude(opus)`. Детект исчерпания **поведенческий**, а не по тексту ошибки (grep по `quota`/`429` в наших логах ловит только SHA): быстрый возврат + пустой журнал + нетронутые отчёты = страйк, два страйка = смена бэкенда. За ночь codex выбило по квоте до 26 августа — **решающий прогон сделал Kimi**, сам, без промта.

Лайны разведены по территориям (winemetal / d3d11 / airconv / ntdll), прогонный слот строго один. Апгрейд живого лайна — только перехватом по PID на границе итерации, никогда убийством лупа во время прогона.

## Что дальше

1. **run6** — длинный A/A на идентичной сборке: нецветной кадр обязан воспроизвестись.
2. **Сохранять сырой RGBA** readback'а: сейчас на диске только агрегат, и `[HYPOTHESIS: логотип Team Cherry]` нельзя превратить в факт.
3. **Интерпретатор на Mono** (`MACRUNNER_HB_JIT_DIRECT_MEM=0`) — у Microsoft это штатный обход для JIT-поверх-JIT, и Мигоцка измерил, что интерпретатор **обгоняет** JIT на этой нагрузке. Бьёт сразу по двум открытым проблемам: порядок памяти для оставшегося спина и разрыв в скорости.

Детектор регрессии для любой правки движка: **readback ordinal-200, ожидаемый чёрный хеш `0xc770038f717d0383` — рабочий фикс делает его нецветным.** Чеклист приёмки — последовательность маркеров оракула до первого видимого пикселя.
