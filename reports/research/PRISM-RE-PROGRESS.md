## ★ Договор эмулятора с системой (найдено по строкам, 04.08)

Интерфейс между ОС и эмулятором — набор обратных вызовов. Для x64 их **всего четыре**:

```
BTCpu64FlushInstructionCache        BTCpu64NotifyMemoryDirty
BTCpu64IsProcessorFeaturePresent    BTCpu64NotifyReadFile
```

**Все четыре у нас реализованы** (проверено по `engine/wine/dlls/`). На уровне договора мы полны.

А у 32-битного эмулятора их двенадцать, и разница говорящая:

```
есть у 32-битного, НЕТ у 64-битного:
  BTCpuNotifyMemoryAlloc       BTCpuNotifyMemoryFree
  BTCpuNotifyMemoryProtect     BTCpuNotifyMapViewOfSection
  BTCpuNotifyProcessExecuteFlagsChange   BTCpuNotifyAffinityChange
  BTCpuFlushInstructionCache2  BTCpuFlushInstructionCacheHeavy
  BTCpuCfgDispatchControl      BTCpuGetBopCode
```

**Для x64 Prism отказался от уведомлений о смене прав страниц.** Сходится с настройками
совместимости («Disable RWX page optimization» — значит по умолчанию ВКЛЮЧЕНА): он держит JIT-память
RWX и права не переставляет, поэтому уведомлять не о чем. У нас 99 584 области памяти на 660
отображений именно из-за перестановки прав — `mprotect` дробит область, ядро macOS обратно не
сливает, 50 201 разрезание не слито.

Прочие говорящие строки: `DispatchJump`, `CodeCacheFlushes`, `BLCKXTAC` (похоже на подпись файла
кэша трансляций).

## Механизм границы ARM64EC (из статей emulators.com)

Выход из ARM64EC в x64 через переходник:

```
X11 = адрес цели
BLR X9    -> проверяльщик вызова: смотрит в БИТОВУЮ КАРТУ EC,
             родной ARM64EC или чужой x64; если чужой — МЕНЯЕТ МЕСТАМИ X10 и X11
             (в X10 лежал адрес второго переходника, зовущего эмулятор)
tail-jump через X11
после возврата: MOV X0, X8     (X8 отображается на RAX)
```

Битовую карту реализует макрос `CFG_ICALL_CHECK_BITMAP` из `kxarm64.h` Windows SDK. У нас
соответствующее — `RtlIsEcCode` и `__os_arm64x_dispatch_call`, оба есть.

`.hexpthk` — Fast-Forward Sequences: крошечные x64-функции без логики, делающие tail-call в
настоящий ARM64EC-код. Нужны для совместимости с приложениями, которые правят прологи функций.

## ★ 2026-08-04 10:35 — АРХИТЕКТУРА КЭША PRISM И НАШ РАЗРЫВ, ИЗМЕРЕННЫЙ

Из работы FFRI («Appearances are deceiving», слайды 17-20) состав подсистемы назван поимённо:

```
xtajit.dll / xtajit64.dll   эмулятор ВНУТРИ процесса
xtac.exe / xtac64.exe       ОТДЕЛЬНЫЙ компилятор, создающий файлы кэша
XtaCache.exe                служба управления кэшем
файлы кэша                  X86_APP.EXE.983D….mp.1.jc

поток: 1) эмулятор сообщает службе через ALPC, что образ загружен
       2) служба ищет готовый файл кэша
       3) нет — компилятор собирает его в ФОНЕ, вне процесса игры
```

Ключевое: **они транслируют один раз в жизни образа, мы — каждый запуск.**

Из разбора внутренностей (blog.checo.cc): типичные накладные расходы Prism —
**вычислительные задачи +20-40%, ввод-вывод +5-15%, смешанные +10-30%**. То есть эмуляция как
таковая ДЕШЁВАЯ. Наш разрыв в 400x — не свойство эмуляции, а наша реализация.

**Наш кэш измерен (прогон 04.08):**

```
попаданий:              87 523   -> доля попаданий 40%
промахов:              130 000
сохранено:              18 337
ПРОПУЩЕНО при сохранении: 111 662  = 86%
   store_skip_multi:     99 791    <- почти всё здесь
   store_skip_unmatched:  11 871
```

**Мы выбрасываем 86% трансляций вместо сохранения.** Причина у 89% пропусков — `multi_helper`.
Отсюда и низкая доля попаданий: кэш просто не наполняется.

**Складывается объяснение 400x, три слагаемых, все наши:**
1. системный слой транслируется при каждом старте (у них CHPE/ARM64X — не эмулируется вовсе);
2. кэш не наполняется на 86% — `store_skip_multi`;
3. горячие циклы уходят в интерпретатор (504 млн вызовов помощников за 308 с, две трети —
   обычные загрузки и записи).

**Первое проверяемое действие:** выяснить, что такое `store_skip_multi` и почему он отбрасывает
99 791 трансляцию. Если это устранимо, доля попаданий вырастет с 40% без единой правки в
кодогенераторе. Счётчик уже печатается — `macrunner-hb-translation-cache-progress`.

## ★★ 2026-08-04 10:40 — ПРИЧИНА ПРОПУСКОВ КЭША НАЙДЕНА: >1 помощник в блоке

`hb_runtime.c:6634`:

```c
} else if (native_blob_helper_call_count(code_buf->code, code_buf->size) > 1) {
    hb_contract_telemetry_record_cache_store_skip_multi();
```

Комментарий рядом (`:6624`): «>1 helper call is the structural restriction in
`native_blob_single_arg_helper_stub`». **Блок, содержащий больше ОДНОГО вызова помощника
интерпретатора, сохранить в постоянный кэш нельзя.**

**Замкнутая цепочка, вся из измеренного:**

```
непереведённые команды          -> вызовы помощников в блоке
                                   (504 млн за 308 с, две трети — обычные LOAD/STORE)
больше одного вызова на блок    -> блок НЕ сохраняется
86% блоков отброшено            -> доля попаданий 40%
кэш не наполняется              -> каждый запуск транслирует заново
```

**Вывод, которого мы раньше не делали: нативный перевод LOAD/STORE окупается ДВАЖДЫ.**
Он не только убирает интерпретатор из горячего пути (ради чего и делался), но и ОТКРЫВАЕТ КЭШ:
блок, из которого ушёл последний лишний помощник, начинает сохраняться и при следующем запуске
не транслируется вовсе. Второй выигрыш никто не считал.

Это же объясняет, почему у Prism кэш работает, а у нас нет: у них блок транслируется целиком в
ARM64, помощников в нашем смысле нет вовсе, поэтому сохраняется всё.

**Проверяемое действие (дешёвое, без правок кодогенератора):** посчитать распределение блоков по
числу помощников. Если основная масса имеет ровно 2-3, то устранение одного-двух семейств
(например векторных LOAD/STORE, которые уже написаны и лежат под выключенными гейтами) переведёт
большую долю блоков через порог и наполнит кэш. Счётчик `native_blob_helper_call_count` уже есть.

**Не проверено:** есть ли обходной путь. Рядом стоит ветка `native_blob_reloc_enabled()` —
«табличный режим», где атрибуция уже сделана раньше. Возможно, в нём ограничение снято. Выяснить
до того, как менять кодогенератор.

## ★★ 2026-08-04 10:50 — РАЗБОР БИНАРНИКА: переходники и вход в эмулятор

Первый настоящий дизассемблер, не чужие статьи.

### `.hexpthk` — Fast-Forward Sequences, 16 байт каждый

```asm
48 8b c4        movq %rsp, %rax
48 89 58 20     movq %rbx, 0x20(%rax)
55              pushq %rbp
5d              popq  %rbp          <- ПУСТЫШКА, ничего не меняет
e9 xx xx xx xx  jmp   <ARM64EC>
cc cc           int3 int3           <- добивка до 16
```

`push rbp; pop rbp` не делает ничего. Байты нужны **для вида**: последовательность выглядит как
обычный пролог функции x64, чтобы программы, правящие прологи ради перехвата, нашли привычную
картину. Документация это утверждает, здесь видно глазами.

Раздел 4368 байт = 273 слота, занято 17.

### Вход в эмулятор (цель первого прыжка, 0x180004000)

Расшифровано по НАШИМ же заголовкам (`winternl.h:351`, структура совпадает):

```asm
ldr x9,  [x18, #0x1788]   ; x9  = TEB->ChpeV2CpuAreaInfo
ldr x9,  [x9,  #0x38]     ; x9  = cpu_area->EmulatorData[1]
cbz x9,  ...              ; NULL -> обходной путь
ldr x10, [x18, #0x1788]
ldr x11, [x10, #0x8]      ; EmulatorStackBase
ldr x12, [x10, #0x10]     ; EmulatorStackLimit
cmp sp,  x11              ; уже на стеке эмулятора?
b.hi ...
```

**У Prism отдельный стек эмулятора, и вход проверяет, не на нём ли уже поток.** Границы хранятся
в области процессора. Плюс он читает `EmulatorData[1]` (смещение 0x38) — у нас это поле НЕ
заполняется вовсе, мы ставим только `ContextAmd64` (0x18) и `EmulatorDataInline` (0x50).

### ★ Расхождение с нашим деревом, связанное с нашим дефектом

`loader.c:385-410`: мы кладём структуру области процессора В НАЧАЛО стека эмулятора (первые 4 КБ),
а затем **временно подменяем границы стека в блоке потока**:

```c
old_stack_limit = teb->Tib.StackLimit;
old_stack_base  = teb->Tib.StackBase;
teb->Tib.StackLimit = cpu->EmulatorStackLimit;
teb->Tib.StackBase  = cpu->EmulatorStackBase;
```

Upstream 11.14 (`unix/thread.c:1238`) держит в блоке потока НАСТОЯЩИЙ стек, а стек эмулятора —
только в области процессора.

**Связь с доставкой исключения.** Наш `macrunner_hb_get_callback_exception_stack`
(`unix/signal_arm64.c:1894`) решает, НА КАКОЙ СТЕК доставлять исключение, сравнивая SP с
границами ИЗ БЛОКА ПОТОКА:

```c
if (sp >= limit && sp < base) return FALSE;   /* limit/base из teb->Tib */
```

А эти границы у нас временно подменены на стек эмулятора. Значит решение зависит от того,
случилось исключение внутри окна подмены или снаружи. Это объясняет и наблюдение прибора
`sp_in_teb=0`, и почему доставка вела себя по-разному в разных прогонах.

**ГИПОТЕЗА (не проверена):** нестабильность доставки исключений связана с этой подменой.
**Дешёвый замер:** печатать в `-record-overlap` не только `teb_stack`, но и признак «границы
сейчас подменены» — сохранить `old_stack_base` в доступном месте и сравнить. Если все сбойные
доставки попадают в окно подмены, гипотеза подтверждена.

**Не путать** с находкой лейна про затёртую текстом область сохранения регистров — это отдельная
вещь, и она измерена, а эта пока только гипотеза.
