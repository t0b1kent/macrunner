# Разбор AOT-кеша Rosetta 2 — 07.08.2026

Кеш стал доступен после того, как оператор снял SIP (`csrutil disable`). До этого
`/var/db/oah` не читался даже под root. Забрано 21 файл `.aot`, 88 МБ, лежит в
`docs/rosetta-aot/`.

Формат: **Mach-O 64-bit arm64 executable**, сегменты `__TEXT`, `__DATA`, `__LINKEDIT` и
дополнительный **`__RUNTIME`**: `vmsize=0x4000`, `filesize=0` — то есть 16 КБ, зарезервированные
и заполняемые нулями при отображении. В файле их нет; наполняет их runtime Rosetta уже в
процессе. Так что «как сшиваются блоки» в содержимом `__RUNTIME` не лежит — ответ в структуре
самого `__TEXT`.

## 1. Барьеров нет вообще — упорядочивание даёт железо

| файл | инструкций | `dmb` | LSE | `ldxr/stxr` | `ldar/stlr` |
|---|---|---|---|---|---|
| `QtCore.aot` | 1 131 832 | **0** | 8653 | 0 | 0 |
| `dyld.aot` | 238 502 | **3** | 84 | 0 | 0 |

Ноль барьеров на миллион с лишним инструкций транслированного x86. Корректно воспроизвести
порядок памяти x86 на слабоупорядоченном ARM без барьеров нельзя — если упорядочивание не
обеспечивает железо. Это аппаратный TSO: бит в `ACTLR_EL1`, который ядро ставит процессу,
запущенному под трансляцией.

**Оговорка:** бит из EL0 не читается, так что это вывод из замера, а не прямое наблюдение.
Других объяснений нулю барьеров нет, но подтвердить напрямую нечем.

Атомарные RMW — исключительно LSE одной командой. Циклов `ldxr/stxr` ноль.

**У нас:** `hb_arm64_codegen.c` ставит `DMB` в 26 местах, трёх видов (`ISH`, `ISHLD`, `ISHST`).
floor24 добавил LSE (`MACRUNNER_HB_LSE_ATOMICS`) — это закрывает только блокирующие RMW.
Обычные загрузки и записи по-прежнему требуют упорядочивания у нас и не требуют у неё.

**Доступен ли бит нам — не установлено.** В `sysctl` ручек нет (`kern.tso`, `kern.actlr`,
`kern.oah` отсутствуют), публичного API нет. Прецедент обратный: FEX-Emu пользуется аппаратным
TSO Apple Silicon под Asahi Linux, то есть железо это умеет для любого процесса — вопрос в том,
даёт ли доступ ядро macOS. Это отдельная задача, и она может стоить больше, чем всё остальное.

## 2. Сшивание блоков — прямое, а не через диспетчер

`dyld.aot`, 238 502 инструкции:

```
b     2851      b.cc  8955      bl   11852
br     129      blr     527     ret   2337
```

**Косвенных переходов 129 на весь модуль.** Блоки связаны прямыми `b`/`bl`, адреса зашиты при
AOT-компиляции. Диспетчера в горячем пути нет.

Это следствие модели: Rosetta компилирует модуль целиком заранее и знает все внутренние адреса.
Наш JIT транслирует по блоку и вынужден проходить через поиск.

## 3. Возврат — теневой стек с проверкой одним сравнением

Типовой возврат:

```asm
ldr  x22, [x4], #0x8          ; снять гостевой адрес возврата с гостевого стека (x4 = RSP)
ldp  x23, x24, [x21], #0x10   ; снять пару (гостевой, нативный) с теневого стека (x21)
sub  x25, x22, x23            ; сошёлся ли гостевой адрес с предсказанным
cbnz x25, <медленный путь>    ; не сошёлся — общий поиск
ret  x24                      ; сошёлся — прыжок сразу по нативному адресу
```

На вызове кладётся пара `stp x24, x25, [x21, #-0x10]!` — гостевой адрес возврата и нативный
адрес продолжения. На возврате пара снимается и сверяется с тем, что реально лежит на гостевом
стеке. Совпало — переход по готовому адресу без всякого поиска. Не совпало (гость подменил
адрес: `longjmp`, раскрутка исключения, самомодификация) — медленный путь.

Частоты в `dyld.aot`: 8650 + 527 укладок против 2337 снятий.

**Распределение регистров:** `x4` — гостевой RSP (по `sub x4, x4, #0x68` и `stur/stp` с
отрицательными смещениями), `x21` — указатель теневого стека, `x24` самый частый регистр
(49 767 упоминаний) — рабочий для адресов.

Отдельно: в коде встречается `bl _mach_msg_destroy_port` — прямой вызов **нативного** символа.
То есть обращения к системным функциям не транслируются, а мостятся напрямую.

## Что из этого можно взять

По убыванию ожидаемой отдачи и по возрастанию риска:

1. **Теневой стек возвратов.** Механизм полностью понятен, локален (кодогенератор вызова и
   возврата), проверяется прогоном. Не требует ничего от системы.
2. **Прямое сшивание блоков** там, где адрес известен на момент трансляции.
3. **Аппаратный TSO.** Отдача наибольшая — снимает 26 мест с барьерами разом, — но доступность
   не установлена и может оказаться закрытой.

**Ни одно из этого не измерено на нашем коде.** Всё выше — разбор чужого двоичного файла и
сопоставление с нашим исходником. Величины выигрыша неизвестны, нужен замер.
