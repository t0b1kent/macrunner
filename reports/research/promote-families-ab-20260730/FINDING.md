# Промоция горячих семейств блоков замедляет запуск в 3 раза

Дата: 2026-07-30. Замер: `scripts/`-обвязка в scratchpad, профили рядом в этом каталоге.

## Результат

| плечо | время до «Restored language» | выборок в `hb_jit_runtime_run` (критический поток) |
|---|---|---|
| `MACRUNNER_HB_PROMOTE_FAMILIES=1` (текущее умолчание) | **770.998 с** | **113** из 536 |
| `MACRUNNER_HB_PROMOTE_FAMILIES=0` | **250.292 с** | **35** из 535 |

Два независимых прибора: настенное время в 3.1 раза, профиль в 3.2 раза. 250 с — лучше
любого ранее записанного прогона (прежний лучший 272 с).

Составляющие на критическом потоке, ВКЛ → ВЫКЛ:

```
hb_jit_helper_exec_two_block_loop   34 → 0
run_jit_block_with_signal_guard     32 → 5
_platform_memmove                   25 → 4
find_region_normalized               8 → 0
```

## Механизм

`try_promote_hot_block_families` заменяет горячий цикл вызовом
`hb_jit_helper_exec_two_block_loop`. Тот пробует три жёстко прописанных быстрых пути
(test/jne epilogue, cmp/rol/test, векторная запись) и, если ни один не совпал, крутит
цикл с `hb_jit_helper_exec_ir_block_once` → `exec_instr_unlocked`, то есть
**интерпретирует блок по инструкции**, с `find_region_normalized` на каждое обращение
к памяти. Непромоцированный блок вместо этого исполняется НАТИВНО через
`run_jit_block_with_signal_guard`.

То есть промоция не транслирует горячий цикл, а подменяет его интерпретатором.

## Побочный вывод: откуда брался разброс метрики

Время до языка гуляло 272 / 321 / 463 / 528 / 750 / 804 с на одной сборке, из-за чего
все A/B были нечитаемы. Похоже, это не шум машины: промоция зацепляла горячий цикл не
на каждом прогоне. Зацепила — уходим к 800 с, не зацепила — к 270 с.

## Статус и что осталось

- n=1 на плечо. Повтор запущен; умолчание менять только после подтверждения.
- Профиль — это 6-секундный снимок на +220 с прогона, а не интеграл по всему запуску.
- 250 с против <45 с у Rosetta: разрыв сжался с ~16x до ~5.5x.

Коммиты: `98632d11` (гейт), `439e5a34` (снят лишний memset снимка контекста).
