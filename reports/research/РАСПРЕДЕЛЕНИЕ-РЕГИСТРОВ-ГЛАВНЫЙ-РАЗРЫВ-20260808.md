# Распределение регистров — главный разрыв с Rosetta (08.08.2026)

Оператор поставил вопрос прямо: Rosetta запускает быстрее, значит мы чего-то не видим.
Не видели. Всё, что я разбирал до этого — барьеры, сшивание блоков, теневой стек — второстепенно
рядом с тем, что нашлось.

## Где живёт состояние гостя

**У нас — в структуре в памяти.** `x19 = ctx`, доступ вида `ldr x21, [x19, #reg_off(RIP)]`.
Постоянного отображения x86→ARM нет: ни `reg_map`, ни закреплённых регистров — поиск по
`hb_arm64_codegen.c` не находит ничего. Эмиссия арифметики использует жёстко закреплённые
временные: `case HB_IR_ADD: emit_add_reg(buf, 22, 20, 21)`. То есть каждая команда x86 это
**загрузить операнды → посчитать → записать обратно**.

**У Rosetta — в регистрах.** Состав `QtCore.aot`, 1 131 832 команды:

| | доля |
|---|---|
| загрузки | 14.8 % |
| записи | 15.0 % |
| арифметика | 38.6 % |

Память трогается втрое реже арифметики. В разобранном фрагменте видно закрепление: `x4` —
гостевой RSP, `x21` — указатель теневого стека, `x24` самый частый регистр (49 767 упоминаний).

Причина, по которой это возможно: у ARM64 тридцать один регистр общего назначения против
шестнадцати у x86-64. Полный набор гостя помещается с запасом.

## Замер нашего раздувания

Из `macrunner-hb-dispatch-stats` и `translation-cache-progress` одного прогона:

```
bytes_stored   = 14 185 644      compile_count = 125 000
total_steps    = 14 250 692 953  total_blocks  = 2 429 000 000
```

```
байт на трансляцию          113.5
ARM-команд на блок           28.4
шагов на блок                 5.87
─────────────────────────────────
ARM-команд на один шаг        4.8
```

**Оговорка о числителе и знаменателе.** `steps` — счётчик шагов IR, ограниченный сверху
`block->instr_count` (`hb_runtime.c:2221`). Если одна команда x86 поднимается в НЕСКОЛЬКО
операций IR — а для x86 это обычное дело, — то шагов больше, чем команд гостя, и настоящее
отношение ARM-команд к командам x86 **выше** 4.8, а не ниже. То есть оценка консервативная.

**У Rosetta аналогичного числа не мерил.** Для этого нужен исходный x86-модуль рядом с его
`.aot`, а в кеше лежат только результаты. Сравнение по составу команд корректно, по раздуванию —
нет.

## Что это объясняет

Разрыв с настоящей Windows в 18–89 раз на одинаковых операциях (`Loaded All Assemblies` 0.278 с
против 17.29 с) записан в CLAUDE.md как «ровный разрыв — производительность, а не поломка».
Ровный множитель по всем операциям — именно то, что даёт постоянная наценка на каждую команду.

И это объясняет, почему сегодняшние находки давали мало:

| что разбирал | измеренная цена |
|---|---|
| обход CFG на диспетчеризации | `avg_scan=1.00` — одна итерация |
| теневой стек возвратов | не окупается по этому основанию |
| барьеры DMB | 26 мест, единицы процентов |
| **раздувание кода** | **×4.8 и выше, на КАЖДОЙ команде** |

## Чего это НЕ значит

Что распределение регистров легко сделать. Это переделка кодогенератора: закрепить x86-регистры
за ARM-регистрами, синхронизировать с `ctx` только на границах блоков и при выходе в помощники,
и сохранить корректность на всех путях, где сейчас читают `ctx` напрямую (обработчики отказов,
SEH, раскрутка, самомодификация). Работа крупная и рискованная.

Но порядок величины теперь известен, и он на порядок больше всего остального.
